  Purpose of Expr vs TypedExpr in Thoxa

  Based on my analysis, here's the current role of each:

  Expr (Untyped Expressions)

  The Expr enum represents the raw AST as parsed from source code, without any type information. It includes:
  - Basic expressions: Number, StringLiteral, Binary, Identifier
  - Type constructs: IntType, TypeDef
  - Control flow: If, Loop, Break, Continue
  - Special forms: Import, Void, TemplateLiteral
  - Type operations: Conversion, CanConvert, TypeGuard

  TypedExpr (Typed Expressions)

  The TypedExpr enum represents the same expressions but with type information attached to every node. Each variant includes a ty: Type field.

  Current Pipeline

  1. Lexing → Tokens
  2. Parsing → Expr (untyped AST)
  3. Type Checking → TypedExpr (typed AST)
  4. Code Generation → Machine code

  Why Both Still Exist

  1. Incomplete Migration: Several Expr variants don't have TypedExpr equivalents yet:
    - Void expression
    - IntType (type construction)
    - TypeDef (module/type definitions)
    - Import statements
    - TemplateLiteral
    - CanConvert expressions
  2. Type Expressions Remain Untyped: Even in TypedExpr, type annotations themselves are still Expr:
  TypedExpr::LetBinding {
      type_expr: Box<Expr>, // Still untyped!
      ...
  }
  3. Fallback Mechanism: The TypedExpr::Untyped variant acts as an escape hatch, allowing the type checker to wrap any Expr it doesn't know how to fully type:
  TypedExpr::Untyped {
      expr: Box<Expr>,
      ty: Type,
  }
  4. Code Generation Duplication: There are parallel code generation paths:
    - src/codegen/expr/ - handles Expr
    - src/codegen/typed_expr/ - handles TypedExpr

  Could Expr Be Eliminated?

  Not easily in the current architecture because:
  1. The parser would need to produce typed expressions directly (not possible without type information)
  2. Type expressions themselves would need a separate representation
  3. Some constructs (like imports, type definitions) don't fit well into the expression-with-type model

  The TypedExpr::Untyped variant suggests this is a transitional state - eventually all expressions could be properly typed, eliminating the need for the fallback and the
   duplicate code generation paths.

  Key Insights:

  7. Tagged Pointer Capacity

  Looking at Thoxa's current tagged pointer scheme:

  Current scheme (low 3 bits):
  - 0b001: Integer (small integer)
  - 0b000: Pointer (heap object)
  - 0b010: False
  - 0b110: True
  - 0b100: Nil (reserved)

  With 3 tag bits, we have 8 possible tags. Currently using 4, leaving 4 available.

  For variant types stored as pointers (tag 0b000), we can use the object header to store unlimited variant discriminators. So:

  - Inline in tag: 4 more types possible (using remaining tag patterns)
  - Via object header: Unlimited variants per type

  For efficiency, we could reserve one more tag pattern for "small variants" of the most common types (like Option).
