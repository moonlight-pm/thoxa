## Intent

Thoxa grew hooks the compiler finds by name. A method called `drop` turns a
type into a shared heap box. A method called `toJson` replaces its encoding,
but only when exported. A method called `view(children:)` makes it a tag.
Joshua, 2026-10-18: "We have a few 'implicit' traits scattered about like
'drop()' -- which is kind of too informal." Alongside the hooks, the compiler
grants abilities by structure (`==`, hashing, encoding) that no code can name,
require, or turn down.

"No traits" was never decided on its merits. The 2026-08 notes rated traits
"should implement" and deferred them; each later feature (Map keys, validation,
codecs, conversions) declined to be the one to pull them in, because "the
compiler can see the concrete type." That holds at a map key or a codec call.
It does not hold inside a generic function, which is next. So traits and
generic functions are designed together, here, and shipped in slices.

Joshua's terms, 2026-10-18:

- "lean toward long-term correct design rather than short term stop gaps."
- Conformance is declared: "we should have to formally declare a type to be
  ordered or hashable or comparable etc."
- Traits over mixins: in Rust "every implementor has to re-implement the
  functions even if they could be implemented in common on the trait." A trait
  carries the shared code; an implementor writes only what it must.
- "rather than impl X for Y i'm thinking 'conform Y to X'".
- Properties: "having getters/setters instead and you might declare a 'get x'
  instead of a 'let x'"; inside an accessor, `field` is the stored value.
- "just use self.. no need to keep inventing new variable names."
- Values of several types in one place are "mixed": `mixed Shape`.

```thx
trait Shape {
    get area: Float64                                       ## required
    fn describe() -> String { "a shape of area {area}" }    ## provided
}

type Circle(radius: Float64)
conform Circle to Shape {
    get area: Float64 { 3.14159 * radius * radius }
}

type Square(area: Float64)               ## the field is the `area` Shape asks for
conform Square to Shape

type Version(major: Int64, minor: Int64, patch: Int64)
conform Version to Equatable, Hashable, Ordered    ## no body: field by field, in order

fn largest<T: Ordered>(items: Array<T>) -> May<T> { … }
fn report(shape: Shape) -> String { shape.describe() }     ## one copy per shape type
type Scene(shapes: Array<mixed Shape>)                      ## circles and squares together
```

## §1 Traits

- `[export] trait Name [: Parent & Parent] { members }` declares a trait.
  Like a type, it is private to its module unless exported, and imported by
  name.
- Members are methods, getters, and setters (§3). A member **without** a body
  is required: every conforming type supplies it. A member **with** a body is
  provided: written once, on the trait, and every conforming type has it.
- A trait adds no fields. It may require a property (`get area: Float64`),
  which a conforming type satisfies with a field or a getter. Two traits that
  give one type a member of the same name are an error (§2); nothing is
  ordered or linearized.
- **Parents.** `trait Ordered: Equatable` means a type conforms to `Ordered`
  only if it also conforms to `Equatable` (declared separately), and
  `Ordered`'s bodies may use `Equatable`'s members.
- **`Self`** is the conforming type, known only through the trait and its
  parents. A signature uses it to say "the same type as the receiver":
  `equals(other!: Self)` on a `Version` takes a `Version`, never a `User`.
- **`self`** is the receiver as a value, typed `Self`. Bare names reach the
  trait's members, as they reach fields and methods in a type body; `self` is
  for the whole value (return it, pass it on, compare it).
- **Checked once, compiled per type.** A provided body is checked at the trait
  against the trait alone (and its parents), so it cannot use anything a
  conforming type might lack, and its free names resolve in the trait's
  module. Each conforming type gets its own compiled copy with `Self` replaced;
  there is no dispatch cost.
- A trait has no type parameters. A trait that needs a related type declares
  it as a member (§7).

## §2 Conformance

```thx
conform Version to Equatable, Hashable, Ordered
conform User to Named {
    fn describe() -> String { "{name} <{email}>" }
}
conform Box<T: Equatable> to Equatable
```

- `conform Type to Trait, … [{ members }]`. Nothing conforms by having members
  of the right names.
- **Where.** In the module of the type or of the trait, nowhere else. A type
  conforms to a trait at most once in a package.
- **Members.** A member in the body goes to the listed trait that declares it;
  a member no listed trait declares is an error (it belongs in the type's
  body). The body may replace a provided member. A required member with no
  implementation is an error, unless the trait has a default for it (§4).
- Inside the body, members are written as in the type's body: fields by bare
  name, `self` for the value, `field` in an accessor (§3).
- **Visibility.** A trait's members are public wherever the type and the trait
  are visible; no `export` in a `conform` body.
- **One name, one member.** A trait member may not share its name with the
  type's own methods, fields, or another trait's members on the same type.
- **Generic types** conform for the instances that meet the bounds:
  `conform Box<T: Equatable> to Equatable` makes `Box<Int64>` equatable and
  leaves `Box<Node>` not. Without bounds, every instance conforms. Its
  members are the instances' methods, only on the instances that conform;
  its associated types are written with the type's parameters
  (`type Cursor = StackCursor<T>`).
- **Built-in types** conform in std, in Thoxa: `conform Int64 to Equatable,
  Hashable, Ordered, Show`, `conform Array<T: Equatable> to Equatable`. A
  program's trait may be given to one in the trait's module; its members are
  written as `extend` methods are (`self` the value), and the built-in's own
  methods count as members. `Array<T>` is a `Sequence` (`ArrayCursor<T>`).
- No blanket conformance (`conform` every `T: Ordered` to `Show`): which types
  conform to what must be answerable from the type's and the trait's modules.
- **Parents** must be conformed too; `conform Version to Ordered` without
  `Equatable` is an error naming it.

## §3 Properties

```thx
type Temperature(kelvin: Float64) {
    get celsius: Float64 { kelvin - 273.15 }
    set celsius(value: Float64) { kelvin = value + 273.15 }
}

type User(name: String) {
    set name(value: String) { field = value.trim() }
    fn rename(to: String) { name = to }        ## through the setter: trimmed
}
```

- `get name: T { body }` declares a getter; `value.name` (and bare `name`
  inside the type) reads it. A getter takes no arguments.
- `set name(value: T) { body }` declares a setter; `value.name = x` on a
  writable place calls it and writes back (a setter is a mutating member,
  D163).
- **Uniform access.** Callers cannot tell a field from a getter, so a field can
  become a getter without changing any caller. std may declare getters on
  built-in types in `extend` blocks; the properties that are runtime primitives
  (`.count`, `.byteCount`) stay primitives (amended at slice 3: a getter over
  them would only add a call).
- **`field`.** An accessor may share its name with a stored field. Then the
  name means the property everywhere (outside code, the type's own methods,
  trait bodies all go through the accessors), and only inside that accessor's
  own body does `field` reach the stored value. A bare `name` there would call
  the accessor itself, so it is an error. A name with no stored field (a
  computed property) has no `field`.
- **Construction goes through setters**: `User(name: "  Ada ")` stores `"Ada"`.
- **Writes from outside.** A stored field stays read-only outside its type
  unless a setter or a trait's `set` requirement makes it writable.
- **In traits.** `get name: T` (required or provided) and
  `set name(value: T)`. A plain field satisfies both a `get` and a `set`
  requirement; declaring the conformance is the opt-in to outside writes.

## §4 Built-in traits

Declared in Thoxa in std's core module, visible in every program without an
import, except `Encodable` and `Decodable`, which live with the codecs in
std/json and are imported to declare (amended at slice 6: core does not
depend on JSON). A **default** is what a body-less conformance gets; it exists only when
every field (every member's payload, for a union) conforms too.

| Trait | Members | Default | Gives |
|-------|---------|---------|-------|
| `Equatable` | `fn equals(other!: Self) -> Bool` | field by field; a union by member, then payload | `==`, `!=` |
| `Hashable: Equatable` | `fn hash(mut hasher!: Hasher)` (added with generic functions; until then no members) | each field into the hasher | Map keys |
| `Ordered: Equatable` | `fn compare(other!: Self) -> Order` | fields in declaration order; union members in declaration order | `<` `<=` `>` `>=`, sorting |
| `Show` | `fn show() -> String` | `Point(x: 1, y: 2)` | `"{x}"` |
| `Encodable` | `fn toJson() -> Json` | today's generated encoding (D182) | `toJson`, `encode`, implicit `Json` |
| `Decodable` | the type's JSON reader | today's generated reader (D182, D191) | `json as T`, `T.read`, `T.readForm`, route body parameters |
| `Component` | `fn view(children: Array<Node>) -> Node` | none | `<Card …>…</Card>` |
| `Resource` | `fn drop()` | none | a shared heap box, `drop` on the last copy, the constructor private to its module (D155, D168) |

- `Order` is `"less" | "equal" | "greater"` (slice 4), ordered by declaration;
  `Hasher`'s surface is settled with generic functions (slice 5).
- Built-ins keep their meaning through std conformances: integers, `Float64`
  (IEEE `==`; `Ordered` gives the total order, settled in its slice), `Bool`,
  `String`, `Bytes`, `Array<T>`, `Map<K, V>`, `Node` (no `Equatable`, as now).
- A `Resource` is not `Equatable`, `Hashable`, `Encodable`, or `Decodable`.
- Operators: `==` / `!=` are `Equatable`, `<` `<=` `>` `>=` are `Ordered`. No
  other operator maps to a trait.
- Compile-time access to a type's fields would let the defaults be written in
  Thoxa; until then the compiler provides them.

## §5 Generic functions and bounds

```thx
fn largest<T: Ordered>(items: Array<T>) -> May<T> { … }
fn unique<T: Hashable>(items: Array<T>) -> Array<T> { … }
type SortedSet<T: Ordered>(items: Array<T>)
extend Array<T: Equatable> { fn contains(item!: T) -> Bool { … } }
fn report(shape: Shape) -> String { shape.describe() }
```

- Type parameters with bounds on functions, methods, types, `extend`, and
  `conform`: `<T: A & B>`.
- **Checked against the bounds.** A generic body is checked once, where it is
  declared; a `T` has only its bounds' members. A call checks that its type
  arguments meet the bounds.
- **Inferred.** Type arguments come from the arguments and the expected type,
  for functions and constructors alike (`Shelf(items: [1, 2])`), and instances
  are made when first used. Explicit arguments, when inference cannot decide,
  are written with `<` glued to the name, which a comparison never is:
  `none<String>()`, `shelf.empty<Int64>()`, `Box<Int64>(value: 1)` (D230).
- Compiled per instance, as generic types are.
- **A bare trait as a parameter type** is a hidden type parameter: `report`
  above is `fn report<S: Shape>(shape: S)`. Each bare parameter is its own
  type, so `overlap(a: Shape, b: Shape)` takes a `Circle` and a `Square`; to
  require one type, write `<T: Shape>(a: T, b: T)`.
- A bare trait anywhere else (a return type, a field, an annotation, a type
  argument) is an error: write a concrete type, a type parameter, or
  `mixed Trait`.

## §6 Mixed values

```thx
type Scene(shapes: Array<mixed Shape>)
type Window(content: mixed Widget)
```

- `mixed Trait` holds a value of any type that conforms, chosen at run time:
  a box holding the value and its type's members. A conforming value converts
  to it implicitly where one is expected.
- Members are called through the box. A member whose parameters mention `Self`
  cannot be called through `mixed`, since the other side's type is unknown
  (`mixed Equatable` has no `==`); every other member can.
- `match` on a mixed value takes one arm per type and requires a catch-all
  arm, since more types can always conform.
- A mixed value is a value: copying it copies (or shares until written) the
  value inside, as other values do. Details settled in that slice.
- Unions stay the closed form (`Circle | Square`); `mixed Shape` is the open
  one.

## §7 Associated types

A trait may declare a related type as a member (`type Element`), named by each
conformance (`type Element = Int64`), and bounds may constrain it with
`where` (`where S.Element: Equatable`; refinements are `where`'s only other
use). The first customer is `for item in value` over user types. Designed here
so traits written before it ship do not change; the surface is settled in its
slice.

Settled in slice 8 (2026-10-19):

```thx
export trait Iterator {                      ## std/core
    type Item
    fn next() -> May<Item>
}
export trait Sequence {                      ## std/core
    type Cursor: Iterator                    ## bounds, like a type parameter's
    type Item = Cursor.Item                  ## fixed: no conformance names it
    fn iterate() -> Cursor
}

type Countdown(from: Int64)
conform Countdown to Iterator {
    type Item = Int64                        ## named once; members write `Item`
    fn next() -> May<Item> { … }
}

fn collect<S: Sequence>(items!: S) -> Array<S.Item> where S.Item: Show { … }
```

- `Item`, not `Element`, which is the built-in HTML type.
- A trait's associated type has bounds (`type Cursor: Iterator`) or is fixed
  as a path of the trait's others (`type Item = Cursor.Item`).
- A conformance names each associated type of the traits it lists, once;
  its members and the trait's provided members write it by name.
- Generic code names them under a type parameter, `S.Item`,
  `S.Cursor.Item`; `where` after the signature bounds them (or a type
  parameter: `where T: Hashable`) or fixes them, `where S.Item == Int64` or
  `== T` (D231). A `where` followed by a name is bounds; a refinement's
  predicates start with an operator or a literal.
- `for item in value`: an `Iterator`'s `next()` is read from a copy until
  `Not`, so `value` does not move; a `Sequence` is read through its
  `iterate()`.
- A member whose signature names an associated type cannot be called
  through `mixed`: each conforming type names it for itself.

## Non-goals

- Conformance by shape (Go-style structural typing).
- Blanket conformances, overlapping conformances, specialization.
- Traits with type parameters (`Convert<T>`); conversions stay `from`
  clauses (D191).
- Traits that add fields or state (mixins).
- Arithmetic operators through traits.
- Implicit conformance of any kind, the built-in traits included.
