## Intent

A type is a predicate on values. JSON `read`, `from` of a runtime scalar, and
in-language construction are introduction forms of the **same** type.
Constraints are refinements of existing types. No Zod schema values, no
combinator library, no traits.

```thx
type Qty = Int64 where >= 1
type CreateOrder(slug: DrinkSlug, qty: Qty)

match CreateOrder.read(req.body.toString()) {
    Fail(e) => jsonErr(e)
    Pass(o) => jsonOk(ticketOf(o))
}
```

## Locks (v0)

### 1. Type-first

Define the input type; `read` / `from` inhabit it. The compiler attaches those
methods (closed table, same family as `"{x}"` and JSX `{e}`). A type that
already defines `read` / `fromJson` is an error.

### 2. Refinements are real types

`Qty` is not `Int64`. `CreateOrder(qty: 0)` is a **type error**. Escape hatch
is explicit and fallible (`Qty.from(n)`).

- **Qty → base is implicit** (`o.qty * price` works). Reverse is not.
- **Refinement subtyping:** `Dozen` inhabits `Qty` when it is strictly tighter
  on the same base. Not the other way.
- **Literal inhabitation:** `let a: Qty = 2` is ok when `2` satisfies.
- **Compile time when the value is known.** Literal `0` against
  `Int64 where >= 1` is a diagnostic. Runtime only for `from` / `read`.
- **Empty refinements are compile errors** (`Qty where <= 0` when Qty is
  `>= 1`).

### 3. `where` syntax

`where` introduces the clause. Inside: `&` and, `|` or, parens group.
Outside `where`, `|` is still a type union.

Range / compare meaning is **by base type**: `Int64` / `Float64` → the value;
`String` / `Array` → `.count`. Catalog v0: compares, inclusive ranges, `!=`,
literal membership. No regex, no email, no predicate closures.

Optional message is a **template** after that conjunct. Holes: `{value}`,
`{expected}`, `{path}`. Unknown holes are a compile error. Omitted → generated
text.

Narrowing a named type intersects clauses:

```thx
type Qty   = Int64 where >= 1
type Dozen = Qty   where <= 12        ## Int64 where >= 1 & <= 12
```

Field-level `where` is allowed (`type Line(n: Int64 where >= 1)`). Type args:
write `May<Qty>`, not `May<Int64 where …>`. Cross-field `where` on the product
itself is **not** v0.

### 4. Closed slugs are literal unions

```thx
type DrinkSlug = "espresso" | "mocha"
```

A string-literal union is a subtype of `String` (same for `0|1` <: Int64,
`true|false` <: Bool). `T.from` / `T.read` check membership. Prefer this over
`String where "a" | "b"` (same check, redundant spelling).

### 5. Inhabitation

| Form | Meaning |
|------|---------|
| `T.read(s)` | JSON string → `Trial<T, Issue>` (syntax via `decode`, then shape + refinements) |
| `T.from(x)` | Runtime base / string → `Trial<T, Issue>` |
| `t.encode()` | `T` → compact JSON `String` |
| `t.toJson()` | `T` → `Json` tree |

Tree **`decode` / `encode` stay** (**D141**). Syntax errors remain
`Trial<Json, String>`. Shape + refinement are `read` / `from`.

### 6. `Issue`

Lives in **`std/json`** for v0 (JSON `read` is the first customer):

```thx
type Issue = Missing | Mismatch | Rejected
```

Fail-fast. Path is dotted. `message(e)` is the user string. Generated
shape/refinement fails are `Mismatch`; written templates and parse errors are
`Rejected`; absent keys are `Missing`. `May<T>` fields: missing or JSON null
→ `Not`.

No `jsonResponse` in `std/json` (HTTP wrap stays in the app).

## Non-goals (punt)

| Item | Why |
|------|-----|
| Collect-all errors | Fail-fast `Issue` is v0 |
| `May<Int64 where …>` | Name the refined type |
| Cross-field product `where` | Not v0 |
| Regex / email / closures | Closed catalog |
| Traits / Zod combinators | Compiler can see the type |
| Changing `decode`’s `Fail(String)` | Tree codec stays D141 |
| Route-clause auto-bind | Call `T.read` from the handler |
