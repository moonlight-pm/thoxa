## Intent

Thoxa has several ways to turn one value into another: implicit coercions at
an expected type (a member into its union, a refined value into its base, an
integer into `Float64`), `T.from(x)` for refined types, `T.fromJson(json)` for
decoding, `t.toJson()` for encoding, and `T(truncating: x)` for bit patterns.
Each has its own name and its own failure type. This freeze gives conversion
one spelling and one rule:

- there is at most one conversion for each pair of types, generated by the
  compiler or declared by the target type;
- `x as T` converts, and its result type says whether the conversion can
  fail;
- `x as? T` converts or returns the failure, exactly `(x as T)?`;
- a conversion happens implicitly only where it cannot fail.

This is Rust's `From` / `TryFrom` without traits: the compiler knows the
pairs, and a type adds its own in its body. Parsing is not conversion. A
`String` can hold JSON or a form, so turning text into a value keeps the
names that say the format (`T.read`, `T.readForm`).

```thx
type Quantity = Int64 where >= 1 & <= 12
type Line(drink: String, quantity: Quantity = 1)

match json as Line {                      ## Trial<Line, Array<Issue>>
    Pass(line) => place(line)
    Fail(issues) => reject(issues)
}

fn ingest(json: Json, requested: Int64) -> Trial<Receipt, Array<Issue>> {
    let line = json as? Line              ## Line, or the Fail returns
    let count = requested as? Quantity    ## the where check, or the Fail returns
    Pass(receipt(line, count))
}

jsonOk(rows)                              ## Array<OrderRow> → Json, implicitly

type Fahrenheit(degrees: Float64) {
    export from(celsius: Celsius) -> Fahrenheit {
        Fahrenheit(degrees: celsius.degrees * 1.8 + 32.0)
    }
}
let hot = Celsius(degrees: 40.0) as Fahrenheit

type Routes {
    POST "/api/orders" (order: CreateOrder) -> Response {
        respond(orders.place(order))      ## a bad body already got a 400
    }
}
```

## Locks

### 1. `x as T`

`as` is a binary operator: an expression on the left, a type on the right.
The type is a name with optional type arguments (`Order`, `Array<Order>`,
`May<Quantity>`); an inline literal union or function type needs a named
alias. `as` binds tighter than `* / %` and looser than unary operators and
postfix `?`, `.`, `[]`, and calls: `a * b as Float64` is `a * (b as Float64)`,
`-x as Int32` is `(-x) as Int32`, and `(json as? Order).lines` needs its
parentheses. (`as` in `import { a as b }` is unchanged.)

The operand is lowered expecting `T` first, so a literal or an existing
implicit coercion gives `T` directly (`[] as Array<Int64>`, `1 as Float64`,
`Circle(radius: 1.0) as Shape`, and `3 as Quantity`, since a literal that
inhabits a refined type is checked at compile time). Otherwise the pair (operand type, `T`) names
one conversion from the table below, or the program is a compile error that
names both types.

| From | To | Result | Notes |
|------|----|--------|-------|
| a union member | its union | `T` | today's implicit injection |
| a literal union | `String` | `T` | today's implicit subtyping |
| a refined type | its base | `T` | today's implicit coercion |
| `Byte`, `Int32`, `UInt32` | `Int64`; any integer → `Float64` | `T` | widening |
| any encodable type (D182 §1) | `Json` | `T` | calls `toJson` (the type's own when it has one) |
| the base | a refined type | `Trial<T, Array<Issue>>` | the `where` check; replaces `T.from` |
| `String` | a literal union | `Trial<T, Array<Issue>>` | membership check |
| `Int64` | `Int32`, `UInt32`, `UInt64`, `Byte` | `Trial<T, Array<Issue>>` | checked narrowing; `Rejected("", "300 does not fit in Byte")` |
| `Json` | any readable type | `Trial<T, Array<Issue>>` | the generated reader (D182 §2, §5); replaces `T.fromJson` |
| `A` | `B` with `from(a: A)` | what the clause returns | §3 |

The `Json` row takes any readable type, not only named products:
`json as Array<Order>` and `json as Map<String, Quantity>` read a top-level
array or map, which D182 could not express (it had no static method to hang
on a structural type).

Not conversions (compile errors with a hint): text into a value
(`text as Order` — write `T.read(text)` or `T.readForm(text)`), `Float64` into
an integer (no rounding rule is chosen), anything into `String` except a
literal union, and keeping low bits (`T(truncating: x)` stays). Implicit
narrowing at an expected type keeps panicking (D167); `as` is the way to
narrow without a panic.

Issue paths are those of D182: `""` for a scalar check, `lines.0.quantity` in
a read.

**Gate:** `conversions_as`, `fail/conversion_missing`, `fail/conversion_text`.

### 2. `x as? T`

`x as? T` is exactly `(x as T)?`: the success value, or the `Fail` returned
from the enclosing function under the existing `?` rules (the residual must
fit the function's return type; compatible `Trial` monomorphs rewrap). `as?`
is one token pair written without a space; `x as ? T` does not parse.

`as?` on a conversion that cannot fail (`rows as? Json`) is a compile error
that says to write `as`: there is nothing to propagate, and the two forms
should not be interchangeable.

**Gate:** `conversions_as_try`, `fail/conversion_try_infallible`.

### 3. `from` clauses

A type body may declare conversions into the type:

```thx
type Fahrenheit(degrees: Float64) {
    export from(celsius: Celsius) -> Fahrenheit {
        Fahrenheit(degrees: celsius.degrees * 1.8 + 32.0)
    }

    export from(json: Json) -> Trial<Fahrenheit, Array<Issue>> {
        let degrees = json as? Float64
        Pass(Fahrenheit(degrees: degrees))
    }
}
```

- A `from` clause has exactly one parameter, the source, and a return type
  that is the type itself (an infallible conversion) or `Trial<Self, E>` for
  any `E` (a fallible one). Nothing else is allowed, and the return type is
  required.
- A clause has no receiver: the type's fields are not in scope, as in a free
  function. It is a constructor, not a method.
- Several clauses take different source types (dispatch as for multi-clause
  functions, D131). Two clauses for one source type are an error.
- `export` makes a conversion usable outside the type's module, as for
  methods. The constructor rule for resource types (D168) applies.
- Only the target declares a conversion into itself. The one exception is
  conversion into `Json`, which the source declares with its own `toJson`
  (D182 §6), since `Json` is not a user type.
- A clause replaces the generated conversion for its pair. A
  `from(json: Json)` clause is the type's reader: `json as T` calls it, and so
  do `T.read(text)` (after decoding) and reads of fields of type `T`. It
  returns `T` or `Trial<T, Array<Issue>>`; a field read moves its issues
  under the field's path (`std/json` `underPath`). This is the custom
  decoding D182 parked.
- A conversion that would make a pair ambiguous (a clause for a pair the
  table already covers implicitly, such as member into union) is an error.

**Gate:** `conversions_from`, `conversions_from_json`, `fail/conversion_from_shape`.

### 4. Implicit conversion to `Json`

Where a `Json` is expected — a parameter, a return, an annotated `let`, a
field, an element of `Array<Json>`, a value of `Map<String, Json>`, a value
inside a `Json` literal (D182 §4) — a value of an encodable type converts as
`x as Json` would. `jsonOk(rows)` replaces `jsonOk(rows.toJson())`.

This is the only new implicit conversion. It cannot fail, it is decided by
the types alone, and it follows the same idea as a member fitting where its
union is expected. Decoding is never implicit: `place(json)` where `place`
takes an `Order` stays a type error, because the failure would need somewhere
to go. A multi-clause function whose clauses take both `T` and `Json` keeps
choosing by the exact type first.

**Gate:** `json_implicit`, `fail/json_implicit_decode`.

### 5. Typed body parameters in route clauses

A route clause parameter whose type is readable, and which is neither a path
capture nor the `Request`, binds the request body. A clause has at most one.

```thx
type Routes {
    POST "/api/orders" (order: CreateOrder) -> Response {
        respond(orders.place(order))
    }

    POST "/orders" (order: Trial<CreateOrder, Array<Issue>>, request: Request) -> Response {
        match order {
            Pass(found) => placed(found, request)
            Fail(issues) => formPage(request, issues)
        }
    }

    GET "/menu" (search: MenuSearch, request: Request) -> Response {
        menuPage(search, request)
    }
}
```

| Request | Read as |
|---------|---------|
| `GET` / `HEAD` | the query string, as a form (`T.readForm(request.query)`) |
| `Content-Type: application/json` | JSON (`T.read(request.body.toString())`) |
| `Content-Type: application/x-www-form-urlencoded` | a form (`T.readForm(request.body.toString())`) |
| any other or no `Content-Type` on a request with a body | `415 Unsupported Media Type` |

When the parameter's type is `T` and the read fails, the clause body does not
run: a JSON request gets `400` with `errorsObject(issues)` as
`application/json`, a form or query gets `400` with `messages(issues)` as
`text/plain`. When the parameter's type is `Trial<T, Array<Issue>>`, the
clause always runs and handles the failure itself (an HTML form page, a
redirect). The generated code names `std/json` and `std/http` items itself,
as D182's codecs do; the module imports nothing new.

**Gate:** `route_body_params`, `fail/route_body_two`.

### 6. One spelling

Once §1–§3 have landed, `T.from(x)` and `T.fromJson(json)` are removed;
`x as T` covers both. `std/`, `examples/`, the sites, and the conformance
tests move to `as` in the same slice. `T.read`, `T.readForm`, `t.toJson()`,
and `t.encode()` stay: the first two parse text, `toJson` is what `as Json`
calls (and what a type defines to own its encoding), and `encode` writes text.

**Gate:** every existing `T.from` / `T.fromJson` gate rewritten with `as`;
`fail/conversion_old_names` (the removed names say what replaced them).

## Non-goals (punt)

| Item | Why |
|------|-----|
| Implicit decoding from context | A hidden failure point; errors are values (§4) |
| Swift's `as?` (yielding `May<T>`) | `?` already means "or return" in Thoxa; `as` gives the `Trial` |
| `x.into()` / target-typed conversion without `as` | No generic functions to need it; `as` names the target |
| Conversions into types the program does not own (std, builtins) | Only the target declares conversions into itself; no orphan rule needed |
| `Float64` → integer conversions | Needs a rounding rule; wait for a sample |
| Generic types (`Page<T>`) as `as` targets | Readers are generated before monomorphization (D182) |
| Route body parameters for other media types (multipart, raw bytes) | Wait for a sample; `Request` stays available |
| A custom failure response for typed body parameters | Take `Trial<T, Array<Issue>>` and respond yourself |
